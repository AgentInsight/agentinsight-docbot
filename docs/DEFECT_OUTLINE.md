# 系统缺陷文档 生成大纲

## 角色定位
你是一名质量工程师，基于测试、生产、用户反馈与监控告警，记录系统缺陷的全生命周期：发现、分级、复现、影响、修复、验证、根因、预防。

## 目标读者
- 开发工程师：关注缺陷详情、修复方案、RCA
- 测试工程师：关注复现步骤、验证结果、回归范围
- SRE：关注线上缺陷处置、影响分析、应急预案
- 产品：关注业务影响、优先级、用户确认

## 章节结构

### 第1章 引言
**目的**：阐明编写目的、适用范围与参考文档。
**要点**：
- 编写目的（面向开发/测试/SRE/产品，定义缺陷全流程）
- 适用范围（系统及版本、缺陷来源：测试/生产/用户反馈/监控告警/安全扫描、缺陷类型：功能/性能/安全/体验/数据/兼容）
- 术语与缩略语（Bug、RCA、SLA、MTTR、DoD）
- 参考文档（需求文档、测试用例文档、性能分析文档、运维手册）
- 版本历史

### 第2章 缺陷概述
**目的**：提供缺陷背景、范围与统计概览。
**要点**：
- 缺陷背景（版本发布、紧急修复、专项治理）
- 缺陷范围（In-Scope / Out-of-Scope）
- 缺陷统计概览（总数、严重缺陷、高优缺陷、已修复、待修复、已关闭、修复平均时长、严重缺陷修复时长）
- 缺陷来源分布（内部测试、生产监控、用户反馈、安全扫描、代码评审）
- 缺陷类型分布（功能、性能、安全、体验、数据、兼容）

### 第3章 缺陷分级
**目的**：定义严重度（Severity）与优先级（Priority）分级标准。
**要点**：
- 严重度分级 S0-S4（S0 阻塞系统不可用、S1 严重核心功能受损、S2 一般非核心异常、S3 轻微体验问题、S4 提示文档问题，含量化标准与示例）
- 优先级分级 P0-P4（P0 立即 4h、P1 高 24h、P2 中 1 周、P3 低 1 月、P4 待定，含响应/修复 SLA 与责任人）
- 严重度×优先级矩阵（确定处置策略）
- SLA 与升级路径（响应/修复/验证/关闭时长，升级链路 Lead → CTO）
- 缺陷分类标签（模块 module-* / 类型 type-* / 层级 layer-* / 来源 source-* / 根因 root-*）

### 第4章 缺陷列表
**目的**：定义缺陷字段规范、清单与详情模板。
**要点**：
- 缺陷字段规范（编号 BUG-NNNN、标题、严重度、优先级、状态、模块、类型、发现人、负责人、发现时间、修复时间、关联需求、关联用例、标签）
- 缺陷清单（编号/标题/严重度/优先级/状态/模块/负责人）
- 缺陷详情模板（基本信息、责任信息、关联信息、标签）
**示例/模板**：
```markdown
### BUG-NNNN <缺陷标题>
- **基本信息**
  - 严重度：S0 / S1 / S2 / S3 / S4
  - 优先级：P0 / P1 / P2 / P3 / P4
  - 状态：New / Assigned / In Progress / Fixed / Verified / Closed / Reopened
  - 类型：功能 / 性能 / 安全 / 体验 / 数据 / 兼容
  - 模块：<模块>
  - 层级：前端 / 后端 / DB / 中间件
- **责任信息**：发现人 / 负责人 / 评审人 / 发现时间 / 期望修复
- **关联信息**：关联需求 / 用例 / 缺陷 / PR / 监控
- **标签**：<label1> <label2>
```

### 第5章 复现步骤
**目的**：标准化复现环境、数据与步骤，确保缺陷可重复。
**要点**：
- 复现环境（Dev/Test/Staging/Prod、URL、后端/前端版本、OS、浏览器、设备、网络、时间）
- 复现数据（用户 ID、请求参数、数据库状态、缓存状态）
- 复现步骤模板（前置条件、操作步骤、期望结果、实际结果、复现概率、复现日志、截图/视频、监控数据）
- 复现要素检查清单（环境/前置/步骤可重复/期望实际对比/日志截图/概率标注）
- 不可复现缺陷处理（收集更多信息、增加埋点、设置观察期、升级处理）

### 第6章 影响分析
**目的**：从业务、用户、技术、合规多维度评估缺陷影响。
**要点**：
- 业务影响（受影响功能、受影响用户数/占比、业务损失量化、SLA 影响）
- 用户影响（受影响用户群、体验降级、数据安全风险、投诉风险）
- 技术影响（受影响模块/接口、数据一致性、系统稳定性、性能影响）
- 合规与安全影响（法规合规、数据保护、安全漏洞 CVE/CWE、审计要求）
- 影响范围量化（错误率、受影响用户数、持续时间、业务损失金额）
- 影响分级（高/中/低，对应紧急/计划/排期修复）

### 第7章 修复方案
**目的**：制定结构化修复方案，含代码变更、测试与回滚。
**要点**：
- 修复方案模板（修复策略、范围、修复人、工时；问题定位根因+故障代码位置；代码变更文件+片段前后对比；修复原理；配置变更；数据变更脚本；测试方案；发布方案含灰度策略；回滚方案；风险评估；评审记录）
- 修复策略选择（直接修复/临时规避/灰度修复/特征开关，场景/优势/风险对比）
- 修复评审检查清单（根因已定位、代码已审查、单元/集成/回归测试通过、性能无劣化、回滚已就绪、文档已更新）
**示例/模板**：
```markdown
### BUG-NNNN 修复方案
- **修复策略**：直接修复 / 临时规避 / 灰度修复
- **修复范围**：<文件 / 模块 / 接口>
#### 代码变更
| 文件 | 变更类型 | 说明 |
|------|---------|------|
| <文件> | 修改 / 新增 / 删除 | <说明> |
#### 变更代码片段
```<lang>
// 修改前
<旧代码>
// 修改后
<新代码>
```
#### 回滚方案
- 触发条件：<列表>
- 回滚步骤：1. <步骤>
```

### 第8章 验证结果
**目的**：定义验证策略、记录验证结果与关闭确认。
**要点**：
- 验证策略（单元测试 100% 通过、集成测试、回归测试无新缺陷、验收测试业务确认、性能测试无劣化）
- 验证结果记录（编号/验证项/验证人/时间/结果 ✅/⚠️/备注）
- 回归测试范围（直接影响模块/接口、间接影响、全量回归关键场景）
- 自动化验证（自动化用例位置、CI 集成、覆盖率、结果报告）
- 用户确认（业务方/产品/客户支持确认、用户反馈跟踪）
- 验证结论（通过/不通过/有条件通过、遗留问题、跟踪事项、关闭条件）
- 关闭确认（修复人/测试人/产品确认矩阵）

### 第9章 预防措施
**目的**：基于根因制定流程、工具、培训、架构层预防措施。
**要点**：
- 预防措施模板（关联缺陷/根因、预防类别、措施描述、责任人、预计完成、验证方式、状态）
- 预防措施分类（流程改进、自动化、工具、培训、架构、规范、测试）
- 流程改进清单（如增加 SQL 评审、强制单元测试）
- Checklist 沉淀（代码评审/测试用例/发布前 Checklist 位置）
- 自动化防护（静态分析 SonarQube、安全扫描 SAST、单元测试覆盖率≥80%、集成测试契约）
- 培训与分享（主题/受众/时间/讲师/材料）

### 第10章 缺陷生命周期管理
**目的**：定义状态机、状态流转规则与责任人矩阵。
**要点**：
- 状态机（New → Assigned → In Progress → Fixed → Verified → Closed / Reopened / Rejected / Duplicate / WontFix）
- 状态定义（每个状态定义、责任人、SLA）
- 状态流转规则（当前状态/允许的下一状态/触发条件/责任人）
- 责任人矩阵（分诊/修复/验证/关闭阶段负责人、协作人、评审人）
- 工具集成（缺陷跟踪 Jira/GitHub Issues/GitLab、代码关联 PR/Commit、CI 集成、监控告警自动建缺陷）

### 第11章 根本原因分析 (RCA)
**目的**：用 5 Whys / 鱼骨图 / FTA 深挖根本原因。
**要点**：
- RCA 模板（关联缺陷、分析人、时间、分析方法；现象描述；5 Whys 分析；根本原因直接/根本/类别；鱼骨图分析；影响因素人员/流程/工具/环境/材料/测量；关联预防措施；经验教训）
- 根因分类（代码缺陷、设计缺陷、流程缺陷、沟通缺陷、环境缺陷、第三方，含占比与典型问题）
- 根因深度评估（L1 现象、L2 直接原因、L3 流程原因、L4 根本原因，含示例）
- RCA 评审（评审人、时间、意见、改进项）

### 第12章 缺陷统计与度量
**目的**：定义关键指标、分布、趋势与度量报表。
**要点**：
- 关键指标（缺陷密度<5/千行、缺陷逃逸率<10%、MTTR S0<4h、重新打开率<5%、修复率>95%、自动化覆盖率>80%）
- 缺陷分布（按模块/类型/严重度/来源/根因）
- 趋势分析（缺陷发现/修复/积压/严重缺陷 30 天趋势）
- 度量报表（缺陷周报、月报、严重缺陷专项、缺陷复盘季度）
- 度量看板（实时看板、关键指标卡、趋势图、钻取分析）
- 度量改进（指标异常分析、改进措施、跟踪闭环）

### 第13章 知识沉淀与复盘
**目的**：建立经验库、复盘机制与培训体系。
**要点**：
- 经验库（编号/主题/类别/来源 BUG-NNNN/链接）
- 复盘机制（触发：S0/S1 缺陷/重复缺陷/系统性问题；时机：关闭后 1 周内；参与：开发/测试/SRE/产品）
- 复盘模板（事件回顾时间线/影响/处置；根因分析；做得好的/不好的；改进项矩阵；经验教训；知识沉淀）
- 培训与分享（主题/来源/讲师/时间/受众/材料）
- Checklist 演进（代码评审/测试用例/发布/运维 Checklist 定期更新）
- 知识传承（新人培训含缺陷案例、文档更新、关键缺陷代码注释）

### 第14章 附录
**目的**：提供模板速查、追踪矩阵与参考资料。
**要点**：
- 缺陷模板速查（详情+复现+修复+RCA 模板汇总）
- 缺陷-用例-需求追踪矩阵（缺陷/关联用例/关联需求/状态）
- 缺陷-根因-预防追踪矩阵（缺陷/根因 RCA/预防 PREV/状态）
- 工具与集成（Jira、GitHub、SonarQube、SENTRY）
- 缺陷分类参考（IEEE 1044、CWE、CVE）
- 参考资料（IEEE 829、ISTQB、《Bug Tracking》Best Practices、Google Testing Blog）

## 写作规范
- 编号约定：BUG-NNNN（缺陷）、RCA-NNN（根本原因）、PREV-NNN（预防措施）、REPRO-NNN（复现步骤）、KB-NNN（经验库）
- 每个缺陷必须关联 PR/Commit/用例/监控
- 严重度基于技术影响客观评估，优先级基于业务紧急度评估
- P0/P1 缺陷必须做 RCA 与复盘
- 缺陷状态流转必须遵循状态机定义
- 经验库持续沉淀，培训持续推广

## 输出格式
- 默认语言：简体中文
- 默认格式：Markdown
- 章节编号：1, 1.1, 1.1.1
- 图表：状态机图、时间线图（用 PlantUML 或代码块表示）
- 表格：使用 Markdown 表格
- 转 Word：`pandoc 本文件 -o 输出.docx --toc --toc-depth=3`
