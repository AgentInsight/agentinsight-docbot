## 1. 引言\n\n### 1.1. 编写目的与详细设计边界\n\n本文档是 agentinsight-researcher 系统的详细设计说明书（Detailed Design Document, DDD），旨在为系统后续的开发、测试、部署与维护提供精确的技术指引。编写目的聚焦于将架构决策分解为可执行的模块设计、接口定义、数据流描述与核心算法逻辑，确保各开发团队对系统实现达成一致理解。\n\n详细设计的边界严格限定于编码与单元测试层面。本文档包含以下内容：\n- **模块级设计**：每个核心模块（如 `src/api/`、`src/graph/`、`src/skills/`）的内部类职责、关键函数签名（含入参/出参类型）、数据结构定义（Pydantic 模型）。\n- **流程设计**：状态图（StateGraph）节点定义、条件边路由逻辑、LLM 调用链路的层次（FAST/SMART/STRATEGIC 三级路由）。\n- **接口设计**：对外 API 的请求/响应 Schema（`/v1/chat/completions` 端点）、WebSocket 消息格式（`/v1/ws/{session_id}`）、MCP 配置 CRUD 接口（`mcp_routes.py`）。\n- **数据设计**：PostgreSQL 表结构（`research_reports`、`uploaded_files`、`mcp_configs`）、Qdrant 集合 schema（`bge-base-zh-v1.5` 768 维向量）、Redis 缓存键设计。\n\n本文档**不包含**以下内容：\n- 项目管理计划、预算估算或商业指标。\n- 用户界面（UI）的像素级设计（前端详细设计由 `frontend/` 项目独立维护）。\n- 系统部署的容器编排细节（由 `docker-compose.yml` 与独立运维文档描述）。\n- 性能压测报告与具体环境调优参数（属于测试与运维环节）。\n\n### 1.2. 项目背景与触发因素\n\nagentinsight-researcher 是一个企业级AI研究分析智能体系统，定位为“中文优先的研究分析智能体”。项目诞生的背景是企业知识管理场景中对**自动化研究报告生成**的强烈需求：传统研究报告撰写依赖人工完成信息检索、多源资料整理、事实核查与多轮修订，耗时且易遗漏关键发现。\n\n触发因素包括以下三方面：\n\n1. **技术趋势推动**：2024年以来，以LangGraph为代表的状态机编排框架成熟，支持构建多智能体协作流水线（Researcher → Writer → FactChecker → Reviewer → Reviser → Visualizer → Publisher）。同时，LiteLLM网关的出现降低了多模型统一调用的复杂性，Qdrant向量库的混合检索能力（BM25 + 向量）为精确召回提供了基础设施。\n\n2. **内部研发需求**：项目团队在RAG（检索增强生成）领域积累的经验表明，单一检索+生成链路在复杂研究场景中存在“上下文窗口溢出”、“事实一致性差”、“多源信息矛盾”等核心问题，需要引入多Agent分工、人在回路（Human-in-the-Loop）、层级化上下文压缩等机制来解决。\n\n3. **开源生态共建**：项目从初始阶段即计划开源，遵循“社区优先”原则。代码仓库 `agentinsight-researcher` 在 GitHub 上公开，采用 Apache 2.0 协议，接受社区贡献。init.sql 中的 MCP 配置描述了 38 个小类的工具集成，其中部分描述（如 firecrawl 标注“14 万星开源神器”）需要统一为中性表述，这体现了项目对文档质量的要求。\n\n### 1.3. 系统范围 In/Out-of-Scope\n\n系统范围定义确保所有利益相关者对边界有一致预期。\n\n**纳入设计范围（In-Scope）：**\n\n| 能力域 | 功能描述 | 证据文件 |\n|--------|----------|----------|\n| 研究报告生成 | **生产级可用性**：系统必须支持高并发、流式响应（SSE）、分钟级故障恢复，并通过 Docker Compose 实现一键部署。设计上优先采用异步编程（`asyncio` + `uvicorn`），所有 I/O 操作（数据库、LLM 调用、搜索、抓取）均以非阻塞方式执行。会话状态通过 `PostgresSaver`（`src/memory/checkpointer.py:16-45`）持久化，支持横向扩展。\n\n2. **中文优先与多源检索**：系统定位为“中文优先的研究分析智能体”，必须深度优化中文语义理解。检索层集成 22 个搜索引擎（国内/国外/学术三区域）和 9 种抓取器（`src/skills/searchers/`、`src/skills/scrapers/`），通过区域自适应路由实现全量信息覆盖。嵌入模型采用 `bge-base-zh-v1.5`（本地 TEI 服务）和 `bge-small-zh-v1.5`（本地 FastEmbed ONNX INT8），确保中文文本的准确表示与高效检索。\n\n3. **模块化与分层隔离**：架构遵循严格的单向依赖原则，`common/` 层不依赖任何业务模块。依赖链为 `api` → `graph`/`agents` → `skills` → `rag`/`llm`/`memory` → `tools`/`common`。同层模块间不推荐互相 import（如 `tools/` 不依赖 `rag/`），共享逻辑下沉至 `common/`。子智能体代码按名称隔离在 `agents/<agent_name>/`、`config/<agent_name>/`、`skills/<agent_name>/` 下，避免跨子智能体直接引用（`src/config/` 目录结构规范）。\n\n4. **数据隔离与安全合规**：所有持久化层（PostgreSQL、Redis、Qdrant）均以 `agent_id` + `user_id` + `session_id` 三级分键实现严格数据隔离。报告查询、删除、额度检查均强制双键过滤（`src/memory/report_store.py:25-40`）。JWT 中间件解析用户身份（`src/api/middleware.py:18-55`），IP 映射生成确定性 `user_id`（`src/api/ip_user_resolver.py`）。敏感配置（API 密钥、数据库凭证）通过环境变量注入，禁止业务代码硬编码。\n\n5. **成本可控与可观测性**：LLM 调用采用三级分层路由（FAST/SMART/STRATEGIC），按任务复杂度动态分配模型，单会话成本追踪通过 `LLMClient.cost_dict` 实现（`src/llm/client.py:60-85`）。可观测性基于 AgentInsight SDK 的 6 类异步 trace span（`src/observability/tracing.py`），涵盖 Agent、生成、工具、检索、链、嵌入全链路。\n\n### 2.2. 总体架构\n\n系统采用分层架构，核心组件及职责如下表所示。架构图由系统根据本节标题自动生成，正文以表格呈现分层与依赖。\n\n| 层级 | 组件 | 职责 | 技术栈 |\n|------|------|------|--------|\n| 输出。会话状态经 `PostgresSaver` 在每次节点执行后自动保存。\n\n### 2.3. 技术栈选型与版本理由\n\n技术栈选型基于“中文优先、生产级、模块化、成本可控”四大原则。核心选型及版本理由如下表（完整矩阵见 `/src/config/settings.py` 及仓库技术栈表）。\n\n| 类别 | 选型 | 版本 | 选型理由 函数不直接操作数据库，仅调用 `conduct_research` 触发图执行。报告数据通过 `report_store.py` 的 `store_report`/`query_reports` 分离查询与写入。\n\n2. **依赖注入与配置管理**：全局配置 `Settings` 类（`src/config/settings.py:20-60`）使用 pydantic-settings 实现单一真源（SSOT）。所有组件通过依赖注入获取配置，如 `LLMClient` 接收 `settings.llm` 参数，避免硬编码。业务代码不应硬编码 URL/密钥（硬编码密钥属硬约束）。\n\n3. **门面模式**：`LLMClient`（`src/llm/client.py`）封装 LiteLLM 的复杂调用，对外暴露 `achat`（普通调用）和 `achat_stream`（流式调用）两个简单接口，屏蔽模型路由、成本计算、重试逻辑等细节。\n\n4. **策略模式**：`PromptFamily`（`src/skills/prompts.py`）实现策略模式，根据语言（默认/英文）选择不同提示模板。`QueryClassifier` 采用规则 + LLM 两层策略，低复杂度请求由规则快速响应，高复杂度请求调用 LLM 判断。\n\n5. **模板方法模式**：`ReportGenerator`（`src/skills/report_generator.py`）定义报告生成骨架（引言→章节→结论），子类通过覆盖特定方法实现多风格/多语言输出。`ContextManager` 的三层路由（L1 Fast Path / L2 BM25Filter / L3 EmbeddingsFilter）同样遵循模板方法模式。\n\n6. **Null Object 模式**：可观测性组件（`src/observability/tracing.py`）在 AgentInsight SDK 未安装时降级为无操作（No-Op），避免空检查。`async def trace_agent(name, ...)` 内部使用 `NullObject` 上下文管理器，调用方无需关心 SDK 状态。\n\n**编码约定**：\n- **命名规范**：类名使用 PascalCase，函数/方法使用 snake_case，私有方法加 `_` 前缀。配置项全大写下划线（如 `MAX_RETRIES`）。\n- **错误处理**：所有外部调用（LLM、数据库、网络请求）必须包裹在 `try/except` 中，统一通过 `common/exceptions.py` 定义的异常类（如 `LLMException`、`RetrievalException`）向上传播。\n- **异步优先**：所有 I/O 操作必须使用 `async def` / `await`，禁止阻塞调用（`requests.get`、`time.sleep` 等）。`src/llm/client.py` 中 `achat_stream` 使用异步生成器逐块流式输出。\n- **日志规范**：统一使用 `structlog`，结构化 JSON 输出到 `stdout`。关键决策点（意图分类结果、检索耗时、成本累计）必须包含 `request_id` 字段。\n\n### 2.5. 关键设计决策与理由\n\n以下列出系统总体设计中的关键决策及其理由，部分决策以 ADR（架构决策记录）形式归档。\n\n**决策 1：LLM 三级分层路由（FAST/SMART/STRATEGIC）**\n- **背景**：不同任务对模型能力需求差异巨大（如简单问候 vs. 深度研究报告），统一调用顶级模型造成成本浪费。\n- **决策**：基于任务复杂度和上下文长度将 LLM 调用分为三级。FAST（如 `zhipuai/glm-4-flash`）用于意图分类、简单对话；SMART（如 `deepseek/deepseek-v4-flash`）用于常规研究生成；STRATEGIC（如 `deepseek/deepseek-v4-pro`）用于深度推理、事实核查、评审修订。\n- **理由**：成本优化（预计降低 60% 以上）、响应速度差异化（FAST 层毫秒级）、质量保证（STRATEGIC 层确保高级任务输出质量）。\n- **后果**：需维护模型路由映射表（`src/config/settings.py:model_tier`），三级模型均需通过 LiteLLM 统一接入与合作方 API 兼容。\n\n**决策 2：BM25 + 向量混合检索 + RRF 融合**\n- **背景**：纯向量检索在短查询、罕见词、精确匹配场景表现不佳；纯 BM25 缺乏语义理解。\n- **决策**：采用 BM25（rank-bm25 + jieba 中文分词）与密集向量（bge-base-zh-v1.5 768 维）混合检索，通过 RRF（Reciprocal Rank Fusion）算法融合结果，支持可选 Rerank（bge-reranker-v2-m3 Cross-Encoder）提升 Top-K 质量。\n- **理由**：结合稀疏检索的精确匹配与密集检索的语义泛化，RRF 融合无需配置权重参数，Rerank 可选避免对 Web 搜索结果过度处理（私有数据场景强制启用）。\n- **后果**：增加了检索管线复杂度（`src/rag/retriever.py`），但提供了 8 类可配置参数（BM25 系数、向量权重、Rerank 阈值等），适应不同业务场景。\n\n**决策 3：上下文压缩三层路由（L1 Fast Path / L2 BM25Filter / L3 EmbeddingsFilter）**\n- **背景**：原始抓取内容可能包含大量无关文本（如页眉、广告、免责声明），直接输入 LLM 浪费 token 且降低分析质量。\n- **决策**：构建三层压缩管线。L1 Fast Path：基于字符长度与关键词匹配快速过滤（<1000 字符直接保留）；L2 BM25Filter：用原始查询对段落进行 BM25 排序，保留 Top-K 段落（密集压缩）；L3 EmbeddingsFilter：用 bge-small-zh-v1.5（512 维 ONNX INT8）对段落嵌入，cosine 相似度过滤，配合滑动窗口去重（`src/skills/context_manager.py:30-80`）。\n- **理由**：L1 零计算成本快速处理短文本，L2 稀疏精确过滤，L3 语义去噪。三层渐进式压缩兼顾速度与质量。本地 FastEmbed 推理无需 GPU，CPU 单次推理 < 5ms。\n- **后果**：L3 输出结果再经 LLM 摘要压缩（滑动窗口摘要），总压缩比可达 20:1 以上，上下文窗口满足 800K 字符限制。\n\n**决策 4：多 Agent 协作——Supervisor 线性 + 条件边模式（Researcher → Writer → FactChecker → Reviewer → Reviser → Visualizer → Publisher）**\n- **背景**：单 Agent 难以完成研究报告的全流程（搜索→写作→核验→审核→修订→可视化→发布），需要专业化分工。\n- **决策**：采用 LangGraph 条件边实现多 Agent 线性子图，每步注入前序 Agent 输出。`FactChecker` 可触发 `Reviser` 修订循环，`Reviewer` 支持人在回路干预（`human_review_enabled` 时推送研究计划至 WebSocket 等待反馈）。\n- **理由**：线性 + 条件边模式控制流透明，每个 Agent 职责单一（如 FactChecker 仅核验引用与数字准确性）。人在回路保障关键决策点可审计。\n- **后果**：需维护 Agent 状态传播（通过 `StateGraph` 的 `add_messages` reducer），`src/graph/` 中定义了 7 个节点和 5 条条件边。`src/agents/` 下每个 Agent 子目录包含独立代码。\n\n**决策 5：数据隔离三级分键（agent_id + user_id + session_id）**\n- **背景**：系统支持多租户（多 Agent 实例、多用户），必须避免数据混淆。同时 Checkpointer 的 `thread_id` 需支持会话级隔离。\n- **决策**：所有持久化操作（PostgreSQL 报告、Redis 缓存、Qdrant 文档集合）均携带 `agent_id` + `user_id` 作为隔离键，`session_id` 用于会话级边界。`Checkpointer thread_id` 预设 `agent_id` 前缀（如 `researcher:user_123:session_456`）。\n- **理由**：粒度可细（用户级）、可粗（Agent 级共享配置），兼顾灵活与安全。MCP 缓存系统 MCP（`agent_id IS NULL`）共享所有 Agent，避免重复注册。\n- **后果**：所有数据访问层（`src/memory/report_store.py`、`src/memory/session_store.py`、`src/rag/qdrant_manager.py`）均需增加 `agent_id` + `user_id` 过滤条件，路由函数 `ip_user_resolver.py` 负责从客户端 IP 生成确定性 `user_id`。\n\n---\n\n## 3. 模块划分\n\n<div class="report-image">\n<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 1024 1024" width="1024" height="1024">\n<defs>\n<linearGradient id="bg" x1="0" `rag/bm25_filter.py`：调用 `BM25Filter.filter()` 进行上下文压缩\n\n同步调用要求被调用方立即返回结果，整个流水线执行流程是同步链式串联，适合确定性流程。\n\n**2. 流式异步通信（SSE / WebSocket）**\n用于高延迟、需渐进式反馈的场景。`api/routes.py` 暴露 SSE 端点（Streaming Response），支持 LLM 生成结果的逐块推送。典型流程：\n- 前端发起 `POST /v1/chat/completions` 携带 `stream: true`\n- `api/routes.py` 创建 `StreamingResponse` 生成器，通过 `async for` 消费 `llm/client.py` 的 `achat_stream()` 输出\n- 每个 token/chunk 通过 `data: {chunk_json}\\n\\n` 格式推送给前端\n- WebSocket 通道（`api/websocket.py`）支持双向推送和接收，用于人在回路审核场景\n\n```python\n# src/api/routes.py 中的流式处理简化伪代码\nasync def stream_generator():\n    async for chunk in llm_client.achat_stream(messages, config):\n        yield f"data: {json.dumps(chunk.model_dump())}\\n\\n"\n```\n\n**3. 图节点函数调用（LangGraph 机制）**\n图内节点之间的“通信”通过 `ResearcherState` 的 `TypedDict` 进行。每个节点函数接收当前状态，经过处理加入新的字段或消息后返回更新后的状态。`add_messages` reducer 确保消息历史被累加。条件边基于状态字段值决定后续路由路径。\n\n同步性方面：\n- **图内节点**：串行执行，一个节点完成并更新状态后，下一个节点才开始\n- **图内并行子图**（如 `Multi-agent`）：通过 LangGraph 的 `Send` 对象实现并行启动，由图框架管理异步并发\n- **WebSocket 反馈**：异步推送，`api/websocket.py` 通过 asyncio.Queue 实现生产者消费者模式，消息发送与图执行异步协作\n- **外部资源访问**：`skills/researcher/mcp_coordinator.py` 通过 asyncio.gather 并发调用多个 MCP 工具，均需等待结果后才进行下一步\n\n通信协议的选型原则为：确定性流程使用同步调用，高延迟/渐近反馈使用流式，人机交互使用 WebSocket。所有模块间通信不引入消息队列或 RPC 框架，保持系统架构简洁，运维复杂度低。\n\n---\n\n## 4. 接口设计\n\n### 4.1. 接口分类：内部/外部/系统\n\nAgentInsight Researcher 复杂业务流程活动\n\n本节以**深度研究（Deep Research）**和多Agent协作为例，用活动描述说明复杂业务流程的节点划分与条件路由。系统会根据本章节标题自动生成SVG活动图。\n\n#### 6.4.1. 深度研究流程（L9-L10递归模式）\n\n深度研究由`src/skills/researcher/deep_research.py`实现，当用户问题复杂度高或需要多角度覆盖时触发。其活动节点如下：\n\n| 活动节点 | 职责 | 输入 | 输出 | 错误处理 |\n|----------|------|------|------|----------|\n| 分析问题 | 基于LLM解析用户查询，提取核心概念与子问题候选 | 原始用户消息 | `analysis_result`：问题结构化表示（主题、实体、时间范围） | 若LLM解析失败，回退至简单关键词提取 |\n| 分解子问题 | 按广度优先/BFS策略生成子问题树，每层最多5个节点 | `analysis_result` | `sub_queries`：子问题列表（含优先级与依赖关系） | 若子问题生成数<1，标记为“叶节点”，直接返回当前上下文 |\n| 递归搜索 | 对每个子问题执行完整的检索-抓取-压缩管道（复用`research_conductor.py`） | 单个子问题 | `learnings`：结构化发现（来源、引用、置信度） | 单个子问题失败不影响兄弟节点，记录warning |\n| 提炼发现 | 合并所有子问题的`learnings`，去重（跨子主题去重：`context_manager.py`的`dedup_across_subtopics`方法） | `learnings`列表 | `merged_learnings`：压缩后的关键发现 | 若合并后为空，回转至深度提高采集范围 |\n| 深度评估 | 检查`merged_learnings`是否足以回答原问题，或是否需要更深层（深度≥10时强制退出） | `merged_learnings` + 当前深度计数器 | 布尔值：`need_deeper`；若需要，`sub_queries`追加新子问题 | 计数器+1，若≥10直接返回当前结果 |\n\n**活动流程的文字描述**：\n1. 入口：深度研究从S2（RESEARCHING）节点派生，当`query_classifier`返回复杂度等级L9或L10时触发。\n2. **分析问题**：调用`src/llm/client.py`的`achat`方法（非流式，模型分配STRATEGIC级别），请求模型输出JSON格式的`analysis_result`。\n3. **分解子问题**：基于`analysis_result`，调用`deep_research.py`的`_generate_sub_queries`方法，采用LLM生成+后处理过滤（去重、排除明显无关项）。\n4. **递归搜索**：对每个子问题，启动`research_conductor.py`的`conduct`方法（内部集成搜索、抓取、压缩），结果存入`learnings`字典（key=子问题，value=发现列表）。\n5. **提炼发现**：调用`context_manager.py`的`compress`方法，执行跨子主题去重（基于BM25相似度阈值0.7）和LLM摘要压缩，输出`merged_learnings`。\n6. **深度评估**：由`_evaluate_depth`函数判断：若`merged_learnings`包含原问题的关键答案片段，返回`need_deeper=False`；否则深度计数器+1，转到步骤2生成更细分子问题。当深度达到10或所有路径都变为叶节点时强制终止。\n\n此递归流程确保复杂问题（如“中国新能源汽车产业链的全球竞争力分析”）通过自顶向下的逐步细化，覆盖政策、技术、市场、供应链等多个维度，而不会跳入无限深度循环。\n\n#### 6.4.2. 多Agent协作流水线\n\n研究流水线的多Agent协作是活动图的另一个核心场景，涉及7个子智能体的有序执行。每个Agent节点均为纯函数，通过StateGraph的条件边连接。\n\n| Agent节点 | 所在文件 | 模型分配 | 超时设定 | 职责大纲 |\n|-----------|----------|----------|----------|----------|\n| AgentCreator | `src/skills/researcher/agent_creator.py` | STRATEGIC (deepseek-v4-pro) | 30秒 | 根据主题动态生成各子Agent的角色描述、工具权限 |\n| Researcher | `src/agents/researcher/`复用图 | FAST (glm-4-flash) | 120秒 | 多源检索、抓取、上下文压缩，调用MCP工具 |\n| Writer | `src/agents/writer/`复用图 | SMART (deepseek-v4-flash) | 90秒 | 基于结构化上下文生成章节草稿 |\n| FactChecker | **AgentCreator→Researcher**：无条件，直接边。\n- **Researcher→Writer**：等待Retriever完成，若检索结果为空（`len(merged_context) == 0`），插入Fallback节点（调用LLM生成通用答复），不进入Writer。\n- 0.6`或`review_comments`包含强制修订标记，路由至Reviser；否则跳至Visualizer（若`image_output_format='svg'`）或直接至Publisher。\n- **Reviser→FactChecker**：修订版本需再次核查（最多2轮），之后无论评分如何均进入评审。\n- **Visualizer→Publisher**：若图像生成失败（捕获异常），`report_images`为空，仍继续发布；若成功，嵌入图片到报告。\n- **Publisher→SF**：完成持久化后终止，返回报告对象。\n\n**并行与并发优化**：\n- Researcher节点内部：22个搜索引擎的调用通过`asyncio.gather`并发执行（`src/skills/researcher/searchers/`中的`search_all`函数），抓取器也按优先级并行启动。\n- Visualizer节点：若报告有多个图片占位，通过`gather`并发调用LLM生成每个SVG，减少总耗时。\n- 检查点（Checkpoint）在每次节点完成后通过`PostgresSaver`异步写入，不阻塞主线程；读取时通过`thread_id`从`checkpoints`表恢复。\n\n---\n\n## 7. 异常处理与日志规范\n\n### 7.1. 异常分级体系\n\n#### 7.1.1. P0（阻断/资源泄漏）\n\nP0 级异常指直接导致服务不可用或系统资源持续泄漏的故障，需要立即响应和修复。在 `agentinsight-researcher` 项目中，P0 异常主要包括：  \n- **未捕获的全局异常**：如中间件层、路由层未处理的 `ValueError`、`KeyError` 等，会导致 HTTP 500 或连接中断。  \n- **资源泄漏**：连接池未释放（`httpx` 连接池、`Playwright` 进程等）、内存碎片累积导致 OOM。  \n- **核心依赖崩溃**：Qdrant 服务不可达、LiteLLM 网关持续超时、PostgreSQL 连接池耗尽。\n\n这些异常在代码中通过 `AgentError` 基类统一捕获（`src/common/exceptions.py:13`），并映射为 HTTP 500/503 状态码。系统日志中启用 `ERROR` 级别立即触发告警。\n\n#### 7.1.2. P1（功能不可用/降级）\n\nP1 级异常影响核心业务流程，但系统可通过降级策略继续运行。典型场景：  \n- **LLM 调用失败**（`LLMError`，`src/common/exceptions.py:38`）：降级链耗尽或模型返回异常格式。  \n- **检索失败**（`RetrievalError`，`src/common/exceptions.py:43`）：向量库或 BM25 索引不可用。  \n- **工具调用异常**（`ToolError`，`src/common/exceptions.py:48`）：MCP 工具执行超时或返回错误。  \n- **Token 预算超支**（`BudgetExceededError`，`src/common/exceptions.py:53`）：节点累计 token 超过分配预算，触发 429 响应。\n\nP1 异常应在上层拦截并尝试降级处理（如跳过工具调用、使用缓存结果），并记录 `WARNING` 日志。\n\n#### 7.1.3. P2（噪声/第三方）\n\nP2 级异常不会影响核心流程，通常来自第三方库或可预见的外部波动：  \n- 网络超时重试（`httpx` 默认重试机制）、单次嵌入请求失败（通过熔断器过滤）。  \n- 搜索引擎不可达（Bocha/Tavily 接口临时错误）、抓取器解析失败（HTML 格式变更）。  \n- 测试页面 Token 输入框为空时降级为 IP-based UserId，属于预期行为。\n\nP2 异常仅记录 `INFO` 或 `DEBUG` 日志，不触发告警，但累计频率异常时可升级为 P1 告警。\n\n### 7.2. 异常处理策略\n\n#### 7.2.1. 重试（Retry）\n\n系统在以下场景实现了自动重试：  \n- **嵌入服务**：`EmbeddingsClient.embed_texts`（`src/rag/embeddings.py`）内置指数退避重试，超时时间 30s，最多重试 3 次。  \n- **搜索引擎调用**：`searchers/*` 模块使用 `tenacity` 库配置重试，重试间隔 1s/2s/4s，仅对 `5xx` 和 `429` 状态码重试。  \n- **数据库操作**：`db_initializer.py` 中的 `CREATE TABLE IF NOT EXISTS` 使用 advisory lock 防止并发竞态，并带有 3 次重试。\n\n重试阈值见配置项 `settings.py` 中的 `RETRY_MAX_ATTEMPTS` 和 `RETRY_BASE_DELAY`。\n\n#### 7.2.2. 熔断（Circuit Breaker）\n\n**嵌入服务熔断器**（`EmbeddingsCircuitBreaker`，`src/rag/embeddings.py:42`）实现了 CLOSED → OPEN → HALF_OPEN 状态机：  \n- `_CIRCUIT_FAILURE_THRESHOLD = 5`：连续失败 5 次开启熔断。  \n- `_CIRCUIT_RECOVERY_TIMEOUT = 60.0`：60 秒后进入 HALF_OPEN 状态，允许一个试探请求。  \n- 成功时调用 `record_success()` 清零失败计数并关闭熔断器；失败时调用 `record_failure()` 累计计数。  \n- 熔断开启时 `is_open()=True`，`embed_texts` 直接抛出 `EmbeddingsCircuitOpenError`（继承 `AgentError`），上层降级使用本地 FastEmbed 或跳过嵌入。\n\n该熔断器在单测中通过时间戳模拟验证（`test_circuit_breaker_half_open_after_recovery_timeout`）。\n\n#### 7.2.3. 降级（Degradation）\n\n降级策略体现在多个层次：  \n- **LLM 三级路由**：`FAST → SMART → STRATEGIC`，当高级模型调用失败时降级使用低级模型。  \n- **检索管道降级**：当 Rerank 服务不可用时跳过重排序，仅使用 BM25+向量 RRF 融合；若 Qdrant 不可用，则降级为纯 BM25（本地内存索引）。  \n- **MCP 工具降级**：当工具调用连续失败（P1 异常）时，跳过该工具并继续执行其他工具，并发调用使用 `asyncio.gather` 并设置 `return_exceptions=True`。  \n- **上下文压缩降级**：L3 EmbeddingsFilter 失败时回退到 L2 BM25Filter，再失败回退到 L1 Fast Path（直接截断上下文）。\n\n所有降级行为记录 `WARNING` 日志，并附带原始异常信息。\n\n#### 7.2.4. 限流（Rate Limiting）\n\n系统实现了两层限流：  \n- **接口层限流**：基于 Redis 令牌桶（`src/config/settings.py` 配置 `RATE_LIMIT_PER_MINUTE`），在中间件层 `middleware.py` 检查，超限返回 HTTP 429。  \n- **资源层限流**：  \n  - 每日报告限额：`daily_report_usage` 表跟踪用户每日生成报告次数，达到 `MAX_REPORTS_PER_DAY`（默认 50）时返回 `BudgetExceededError`（HTTP 429）。  \n  - Token 预算分配：`TokenBudgetAllocator`（`src/llm/token_budget.py`）为每个会话分配 token 预算，节点累计超支立即抛出 `BudgetExceededError`，防止单个请求消耗过多资源。\n\n限流阈值可在环境变量中动态调整，重启后生效。\n\n### 7.3. 错误码体系\n\n错误码按模块分段，采用 `ERR-{模块缩写}-{4位数字}` 格式。模块缩写与对应范围如下：\n\n| 模块缩写 | 范围 | 对应模块 |\n|---------|------|--------|\n| CONF | 0999 | 分位）衡量端到端请求耗时。典型场景包括：\n- 简单对话（CHAT 分类）：P50 < 500ms，P95 < 2s，P99 < 5s；\n- 研究报告生成（RESEARCH 分类）：因涉及多源检索、并发抓取与 LLM 流式生成，P50 < 15s，P95 < 40s，P99 < 60s；\n- 流式首包时间（TTFB）：P50 < 1s。\n\n**吞吐量** 以每分钟请求数（RPM）和每分钟 token 生产量（TPM）计量。单节点预期承载：\n- 对话类请求: 500 RPM；\n- 研究类请求: 20 RPM（受 LLM API 速率与搜索并发限制）。\n\n**资源消耗** 关注 CPU 使用率、内存占用、网络 IO 和数据库连接数。核心容器内存限制为：agent 服务 4GB、Qdrant 2GB、Redis 512MB、PostgreSQL 1GB。峰值内存不应超过限制的 80%。\n\n**可用性** 以 API 端点 `/v1/chat/completions` 的 5xx 错误率 < 1% 为目标，且单次请求内 LLM 调用失败自动重试（`src/llm/client.py:LLMClient.achat_stream` 内置指数退避重试逻辑）。\n\n### 8.2. 容量规划与扩容路径\n\n容量规划基于历史流量峰值与业务增长预测，采用水平扩展为主的策略。系统组件分为无状态和有状态两类，分别制定扩容路径。\n\n**无状态服务**（agent 服务、前端）：\n- 通过 Docker Compose 或 Kubernetes 增加副本数。当前部署使用 7 容器架构，agent 服务为单副本瓶颈。扩容方案为：横向增加 agent 容器，前端通过 Nginx 按 `agentName` 路径分发（`frontend/nginx.conf` 已预留多 worker 配置）。\n- LLM 网关层（LiteLLM）本身支持多个模型端点的权重路由，可通过 `src/config/settings.py` 中的 `LLM_ENDPOINT_WEIGHTS` 配置多 provider 负载均衡。\n\n**有状态服务**（PostgreSQL、Qdrant、Redis）：\n- **PostgreSQL**：读写分离。Checkpointer 核心表（`src/memory/checkpointer.py` 使用的 `checkpoints` 表）写入频繁，建议配置 PgBouncer 连接池并启用 `BRIN` 索引。`src/memory/session_store.py` 中的会话查询按 `agent_id`+`user_id` 过滤，已添加复合索引 `idx_session_agent_user`。\n- **Qdrant**：向量搜索为 CPU 密集型。`src/rag/qdrant_manager.py` 使用 namespace 隔离，每个 agent 独立集合。扩容方案为：增加 Qdrant 节点并通过 gRPC 负载均衡，同时调整 `ef_construct` 参数平衡写入速度与召回率。\n- **Redis**：用于热点缓存（`src/llm/token_budget.py` 中 `TokenBudgetAllocator` 使用 Redis 存储会话级 token 预算）、速率限制（`src/api/middleware.py` 中的 `rate_limiter`）和短期会话存储。Redis 集群模式可横向扩展，但单机 512MB 通常足够。\n\n**扩容触发条件**：当 P99 延迟超过阈值持续 5 分钟，或 CPU 使用率 > 80% 持续 10 分钟，或 5xx 错误率 > 2% 时，自动触发扩容告警。垂直扩容（增大容器资源配额）作为临时方案，优先采用水平扩容。\n\n### 8.3. 优化策略：缓存、队列与索引\n\n系统已实施多项性能优化，覆盖缓存、并发控制和索引设计。\n\n#### 8.3.1. 缓存体系\n- **Redis 热点缓存**：`src/llm/token_budget.py` 将用户会话的 token 预算缓存至 Redis，TTL 设置为 30 分钟，避免频繁查询 PostgreSQL。`src/memory/session_store.py` 中会话元数据也缓存到 Redis，键模式 `session:{agent_id}:{user_id}:{session_id}`。\n- **BM25 索引缓存**：`src/rag/retriever.py` 中的 `BM25Index` 使用 `functools.lru_cache` 缓存每个 namespace 的索引对象，减少重复构建开销。`src/config/settings.py` 中 `BM25_CACHE_MAXSIZE=32` 限制无界增长（原 P1 优化项 `WrittenContentCompressor._chunk_cache` LRU 容量限制，见 `src/rag/context_manager.py`）。\n- **LLM 响应缓存**：`src/llm/client.py` 支持 `use_cache` 参数，对幂等请求（如 Rerank 结果）启用 5 分钟本地缓存，减少重复 API 调用。\n\n#### 8.3.2. 队列与异步处理\n- 系统基于 FastAPI 异步框架，LLM 流式生成通过 `async generator` 实现，避免阻塞事件循环。`src/api/routes.py` 中的 `chat_completion` 端点使用 `StreamingResponse`，每 token 生成后立即 yield。\n- 深度研究报告生成（`src/skills/researcher/deep_research.py`）采用递归子查询树，每个子查询通过 `asyncio.gather` 并发执行，`worker` 数量由 `DEEP_RESEARCH_CONCURRENCY=5` 控制。搜索与抓取阶段（`src/skills/researcher/research_conductor.py`）使用 `asyncio.Semaphore` 限制并发抓取数为 15，防止下游服务过载。\n- 未显式引入消息队列，但未来计划：将研究报告的完整生成流程（尤其是包含图片生成、事实核查等耗时步骤）异步化到 Celery 或 Redis Streams 中，以释放 API 线程。\n\n#### 8.3.3. 索引优化\n- **PostgreSQL 索引**：`src/memory/db_initializer.py` 在 `research_reports` 表创建复合索引 `(agent_id, user_id, created_at DESC)`，覆盖报告列表查询；`checkpoints` 表按 `thread_id` 建唯一索引，查询速度 < 5ms。\n- **Qdrant 索引**：`src/rag/qdrant_manager.py` 创建集合时指定 `vectors_config` 为 HNSW 索引（`m=16, ef_construct=200`），并开启 `quantization` 为 `scalar` 以降低内存占用。针对 namespace 隔离，一个 agent 使用一个 collection，避免全量扫描。\n- **BM25 索引**：`src/rag/retriever.py` 中的 `BM25Okapi` 索引在第一次检索时按 `namespace` 构建，之后增量更新。`src/config/settings.py` 中 `BM25_REINDEX_INTERVAL=3600` 秒，避免频繁重建。\n\n### 8.4. 瓶颈分析与优化\n\n通过压测与生产监控，已识别出以下主要瓶颈并完成部分修复。\n\n#### 8.4.1. 已修复瓶颈（第一轮优化）\n- **内存泄漏**：`src/rag/context_manager.py` 中 `WrittenContentCompressor._chunk_cache` 未设置 LRU 上限，导致 RAM 无界增长。修复：引入 `@lru_cache(maxsize=256)`。`src/llm/client.py` 中 `LLMClient` 的 `httpx` 连接池未限制，修复为 `max_keepalive_connections=20`。`src/skills/workers/playwright_scraper.py` 未关闭 browser context，修复为 `async with BrowserContext()`。\n- **Qdrant 连接超时**：`src/rag/qdrant_client.py` 默认超时 5s 在峰值不足，修复为根据文档量动态计算 `timeout = max(5, doc_count // 100)`。\n- **Postgres advisory lock 竞态**：`src/memory/db_initializer.py` 启动时使用 `pg_advisory_xact_lock` 防止并发初始化，但锁未释放导致后续连接阻塞。修复为 `try_lock(timeout=10)` 模式。\n\n#### 8.4.2. 待优化瓶颈（剩余 9/52 项）\n- **启动期内存峰值**：`_warmup_fastembed`（`src/rag/fastembed_client.py`）与 `_warmup_graph`（`src/graph/graph_compiler.py`）并发加载模型与状态图，导致内存峰值超过限制。方案：顺序化预热，并设置 `WARMUP_FASTEMBED_BEFORE_GRAPH=true`。\n- **SSE 双重累积**：`src/api/stream_handlers.py` 中 `collected_content` 与 `final_state` 同时缓存完整响应，造成冗余内存。方案：合并为一个完整响应对象，使用 `orjson` 序列化。\n- **DeepResearch 递归返回**：`src/skills/researcher/deep_research.py` 中递归树完整保存至状态，对于深度 > 5 的树，状态大小可达 10MB。方案：仅保存叶子节点摘要，父节点使用引用指针。\n\n#### 8.4.3. 监控体系\n- 集成 AgentInsight SDK（`src/observability/tracing.py`）生成 6 类 trace span，可追踪每个请求的 LLM 调用、工具执行、检索步骤耗时。\n- 关键告警项：内存使用率 > 80% 持续 2 分钟、P99 延迟 > 阈值、5xx 错误 > 2%。日志采样率 100% 用于 trace，错误日志单独聚合。\n\n### 8.5. 压测方案\n\n压测是验证性能指标和发现瓶颈的核心手段。本系统支持三种压测工具：k6、JMeter 和 Locust，团队可根据场景灵活选择。\n\n#### 8.5.1. 压测环境与基线\n- **硬件**：与生产环境一致或 1/2 缩配（4C8G 虚拟机）。\n- **数据准备**：预填充 100 个 Agent 配置、每个 Agent 下 100 个会话、每个会话 10 条历史消息；Qdrant 导入 10,000 条文档嵌入。\n- **压测端点**：`/v1/chat/completions`（POST），使用包含研究意图的典型 prompt（如“请分析新能源汽车市场趋势”）。\n\n#### 8.5.2. k6 方案（推荐，轻量脚本化）\n- 脚本位置：`tests/performance/k6_script.js`（示例路径，实际项目中应维护）。\n- 场景定义：\n  - 稳态负载：10-20 虚拟用户 (VU)，持续 5 分钟，观察 P50/P95/P99。\n  - 峰值负载：从 10 VU 线性增加到 50 VU，持续 3 分钟，观察错误率与限流触发。\n  - 阶梯负载：每 30s 增加 5 VU，直到 P99 超过 10s 或 5xx > 5%，记录最大并发数。\n- 指标验证：吞吐量、响应时间、`http_req_duration` 百分位、`http_req_failed` 率。\n\n#### 8.5.3. JMeter 方案\n- 使用 `Test Plan` 配置线程组（Thread Group）模拟并发用户，通过 CSV Data Set Config 提供不同 prompt。\n- 监听器：`Summary Report`、`Aggregate Report`、`Response Times Over Time`。\n- 断言：检查响应状态码 200 并包含 `"choices"` 字段，流式响应需校验 `Transfer-Encoding: chunked` 头部。\n\n#### 8.5.4. Locust 方案\n- 编写 `locustfile.py`，继承 `HttpUser`，定义 `chat_completion` 任务。\n- 使用 `@task(weight)` 分配对话与研究请求比例（7:3）。\n- Web UI 实时查看 RPS、响应时间、失败率。可与 Prometheus 集成导出指标。\n\n#### 8.5.5. 压测注意事项\n- 流式端点需使用 `stream=True`，否则会等待完整响应导致客户端 OOM。\n- LLM 调用使用 mock 模式（`USE_MOCK_LLM=true`）以消除外部依赖，专注于系统内部瓶颈。\n- 压测前先执行 `pytest tests/performance/ -v -m performance` 运行已有的性能单元测试（如 `test_memory_growth`、`test_concurrent_requests`），确保无回归。\n- 压测结果记录至 `tests/performance/results/`，每次压测附带提交 SHA 与测试参数。\n\n通过上述方案，系统可持续验证性能指标、发现并消除瓶颈，并为容量规划提供数据支持。\n\n---\n\n## 9. 部署设计\n\n<div 实例。核心拓扑如下：\n\n| 容器名称 | 镜像源 | 暴露端口 | 职责 | 依赖关系 |\n|----------|--------|----------|------|----------|\n| agent | `agentinsight/agent:latest` | 8000 | FastAPI 应用服务，运行 LLM 编排引擎、RAG 管道、API 路由等 | 依赖 embeddings、qdrant、redis、postgres、searxng（以及可选的 rerank） |\n| embeddings | `ghcr.io/huggingface/text-embeddings-inference:1.5` | 8080 | 提供远程 Embedding 推理服务（bge-base-zh-v1.5，768 维） | 无外部依赖 |\n| qdrant | `qdrant/qdrant:v1.18` | 6333 | 向量数据库，支持混合检索与 namespace 隔离 | 挂载持久化数据卷 |\n| redis | `redis:8.0-alpine` | 6379 | 缓存、限流、短期会话状态 | 无外部依赖 |\n| postgres | `postgres:16-alpine` | 5432 | 关系数据库，用于 LangGraph Checkpointer 持久化、业务元数据存储 | 挂载持久化数据卷 |\n| searxng | `searxng/searxng:latest` | 8888 | 自托管搜索引擎实例，作为可选搜索源 | 无外部依赖 |\n| rerank（可选） | `ghcr.io/huggingface/text-embeddings-inference:1.5` | 8081 | 提供 Rerank 推理服务（bge-reranker-v2-m3） | 无外部依赖 |\n| frontend | `agentinsight/frontend:latest` | 3000 | Next.js 15 前端静态渲染（SSR），通过 Nginx 反向代理分发 | 依赖 agent API |\n\n各环境共享同一代码库，通过不同 Docker Compose 覆盖文件（`docker-compose.override.yml`）和环境变量文件（`.env.*`）差异化配置。\n\n| 环境 | 目的 | 构建模式 | 关键配置差异 | 数据隔离 |\n|------|------|----------|--------------|----------|\n| Dev | 本地开发调试 | 开发模式（热重载） | 启用 debug 日志，使用 SQLite 或内存 Checkpointer，禁用真实搜索与 LLM 调用（mock 模式） | 无持久化，数据存放在临时目录 `temp/` |\n| Test | 自动化测试与 CI | 测试模式（QA 离线） | 使用独立 Qdrant/PostgreSQL 实例，部署时不联网拉取外部模型，Embedding 使用本地 ONNX FastEmbed，Rerank 关闭 | 测试数据预填充，测试后清理 |\n| Staging | 预发布验收 | 生产离线模式 | 使用生产数据库副本（脱敏），启用全链路 LLM 但限制请求频率，开启 AgentInsight 可观测性 | 写操作限制到独立数据库 schema |\n| Prod | 线上正式服务 | 生产联网模式 | 启用所有搜索源与抓取器，LLM 不限流，开启缓存预热，配置高可用副本 | 所有持久化数据严格按 `agent_id`+`user_id` 隔离（`src/memory/report_store.py:30-45`） |\n\n部署时通过环境变量 `APP_ENV` 控制配置加载。以 `docker-compose.yml` 为基础，通过 `-f docker-compose.yml -f docker-compose.prod.yml` 叠加配置。关键环境变量模板存储在 `deploy/env/` 目录下，包含示例密钥、数据库连接字符串等，Vault 或 .env 文件在 CI/CD 阶段注入。\n\n环境之间的数据迁移遵循以下策略：\n- 数据库 schema 变更通过 Alembic 迁移脚本执行，所有环境共享迁移序列。\n- 向量库索引重建在 Staging 环境验证后再于 Prod 环境执行。\n- 用户数据跨环境流动仅允许从 Prod 脱敏副本至 Staging 用于性能测试。\n\n### 9.2. 部署流水线蓝绿金丝雀\n\n系统采用双阶段部署流水线：CI 阶段（代码合并后触发）和 CD 阶段（推送至 release 分支或人工审批后触发）。流水线定义在 `deploy/ci/github-actions.yml` 中（实际路径可能为 `.github/workflows/deploy.yml`）。\n\n**CI 阶段**：\n1. 代码合规检查（Pylint、MyPy、Sourcery）。\n2. 单元测试（96 个用例）与集成测试（基于 Test 环境 Docker Compose）。\n3. 构建 Docker 镜像并推送至私有 Registry（镜像标签为 `agent:GIT_SHA-frontend:GIT_SHA`）。\n4. 生成安全扫描报告（Trivy）。\n\n**CD 阶段**：支持三种部署模式，通过环境变量 `DEPLOY_STRATEGY` 选择：\n\n| 策略 | 适用环境 | 流程 | 回滚方式 |\n|------|----------|------|----------|\n| 蓝绿部署 | Staging / Prod | 维护两套完整环境（蓝、绿）。新版本部署至空闲环境后，运行健康检查（`GET /health`），通过后将 Nginx 上游切换至新环境。切换后保留旧环境 30 分钟作为回滚缓冲区。 | 立即修改 Nginx 配置指向旧环境（`deploy/nginx/switch.sh`） |\n| 金丝雀部署 | Prod | 新版本灰度发布至一小部分请求（如 5%）。通过 Nginx `split_clients` 模块按请求 User‑Agent 或 IP hash 分配，结合 Prometheus 安全设计\n\n本章节定义系统的安全模型、身份与访问管理（IAM）机制、数据安全策略、威胁建模方法、合规要求以及审计日志的不可篡改保障。所有安全设计遵循“默认安全”、“最小权限”和“纵深防御”原则，并严格满足个人信息保护法和通用数据保护条例的合规要求。\n\n### 10.1. 安全模型：零信任与多层防御\n\n系统采用**零信任**安全模型，核心原则是“永不信任，始终验证”。在网络层、应用层和数据层均建立了多层防御机制，以应对内部和外部威胁。\n\n**零信任的实现：**\n- **身份验证**：所有API请求（包括内部服务间调用）都必须通过JWT令牌认证。中间件服务负责解析令牌并将解析后的`user_id`注入请求上下文，作为后续所有操作的基准身份。\n- **权限隔离**：数据访问严格基于`agent_id`（租户维度）、`user_id`（用户维度）、`session_id`（会话维度）的三级隔离策略。所有持久化操作，如报告查询、会话管理、MCP缓存，都强制带上这三把“锁”，确保一个用户无法访问另一个用户的数据。\n- **持续验证**：每个请求在进入核心业务逻辑前，都会经过意图分类器（`src/skills/researcher/query_classifier.py`），将输入划分为RESEARCH、CHAT或OFF_TOPIC，防止非预期操作。对于涉及工具调用的场景，需要经过权限校验和输入清洗。\n\n**多层防御架构：**\n防御层如下图所示，每层都有独立的安全控制点，即使某一层被突破，后续层仍能提供保护。\n\n| 防御层 | 关键组件 | 安全职能 |\n| :--- | :--- | :--- |\n| **1. 传输与边界层** | Nginx, HTTPS, 安全响应头 | 强制HTTPS连接；设置`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Strict-Transport-Security`等安全头；生产环境关闭Debug模式。 |\n| **2. 应用入口层** | FastAPI中间件 (`src/api/middleware.py:24`) | JWT身份解析；请求ID注入；速率限制；CORS策略控制。 |\n| **3. 业务逻辑层** | Pydantic校验, 查询分类器 | 对所有外部输入（包括用户消息、文件上传、工具调用的参数）进行严格的Pydantic模型校验；在进入研究流水线前，对用户意图进行多级分类，过滤恶意或越界指令。 |\n| **4. 工具与数据访问层** | MCP协调器 (`src/skills/researcher/mcp_coordinator.py`), 检索器 | 工具调用权限严格划分为`read`、`write`、`execute`、`network`四类，LLM必须显式声明所需权限；禁止`eval`/`exec`执行用户输入；LLM输出在被传递给下一个工具前，必须经过结构化校验。 |\n| **5. 数据存储层** | PostgreSQL, Redis, Qdrant | 数据加密存储；PII脱敏；基于租户和用户的数据隔离；审计日志的不可篡改性。 |\n\n### 10.2. 身份与访问管理（IAM）\n\n系统的IAM模型基于**OAuth 2.0**思想，使用**JWT**作为身份凭证，并实现**基于角色的访问控制（RBAC）** 和细粒度的权限管理。\n\n**核心流程：**\n1.  **身份验证**：外部请求携带JWT令牌。`src/api/middleware.py`中的`inject_user_id`函数解析JWT，提取`user_id`和`role`等信息。令牌本身不持久化存储，仅保留解析后的必要身份信息。\n2.  **授权与角色**：当前主要通过`user_id`实现简单的用户级隔离。系统预留了`role`字段，为未来实现完整的RBAC模型（例如`admin`、`analyst`、`viewer`等角色）打下基础。角色权限控制着对API端点（如MCP配置管理）和敏感数据操作（如删除报告）的访问。\n3.  **密钥管理**：\n    -   **API Key**：用户用于访问OpenAI兼容接口的密钥。密钥在执行BCrypt哈希（cost=12）后进行持久化存储，防止明文泄露。API Key在创建时仅返回一次原文。\n    -   **服务端密钥**：如用于JWT签发的`SECRET_KEY`、数据库密码、第三方服务API Key等，通过环境变量注入，严禁硬编码在代码中或写入日志。项目`scripts/init.sql`中所有密钥均为`<your-token>`占位符，符合安全最佳实践。\n\n### 10.3. 数据安全：加密与脱敏\n\n数据安全策略覆盖数据的传输、存储和使用全过程，核心是加密和脱敏。\n\n**1. 传输加密：**\n-   生产环境强制使用**HTTPS**，由Nginx层终止SSL/TLS。\n-   内部服务间通信，根据部署环境的安全性，也推荐启用TLS。\n\n**2. 存储加密：**\n-   **密钥与密码**：用户密码采用**BCrypt (cost=12)** 进行哈希存储。API Key使用**SHA256+BCrypt** 双哈希，极大增加彩虹表攻击的难度。\n-   **会话内容**：用户与大模型对话的原始内容被视为敏感信息。其在PostgreSQL中存储时，进行了应用层加密。系统通过配置指定加密算法和密钥，确保即使数据库被攻破，会话数据也无法被直接解读。\n-   **业务数据**：其他敏感配置（如MCP的`env_vars`）在存储于PostgreSQL前，也推荐进行应用层加密，当前项目已规划此增强。\n\n**3. 日志与响应脱敏：**\n-   **日志脱敏**：所有日志记录，包括搜索日志（`search_logs`表）和审计日志，会在写入前对PII（如`<your-token>`占位符对应的真实值、用户邮件地址、会话内容摘要）进行脱敏处理。例如，用户IP只记录前三段。\n-   **API响应脱敏**：任何API响应（包括错误响应）都禁止返回密码、密钥或令牌的原文。用户通过JWT令牌获取服务，服务端不会在响应中重新暴露令牌内容。\n\n### 10.4. 威胁建模：STRIDE\n\n系统使用微软的**STRIDE**威胁模型进行系统性安全分析，以识别和缓解潜在风险。\n\n**STRIDE 威胁分析与缓解措施：**\n\n| 威胁类别 | 具体风险 | 缓解措施 |\n| :--- | :--- | :--- |\n| **S**poofing (身份欺骗) | 攻击者伪造JWT令牌或用其他用户身份发起请求。 | 建立严格的JWT验证中间件；使用强加密算法签发令牌；API Key双哈希存储。 |\n| **T**ampering (篡改) | 攻击者拦截或修改API请求/响应内容；非法修改数据库中的报告或审计日志。 | 强制HTTPS保证传输完整性；审计日志设计为仅追加（append-only），防止事后篡改。 |\n| **R**epudiation (抵赖) | 用户否认其执行的操作（如创建高风险报告）。 | 所有用户操作均记录在不可篡改的审计日志中，包含时间戳、`user_id`、操作类型和参数摘要。 |\n| **I**nformation Disclosure (信息泄露) | PII泄露；会话内容泄露；系统内部配置（如API Key）泄露。 | 数据加密存储和传输；日志脱敏；最小化数据收集原则；禁止在响应中返回密钥。 |\n| **D**enial of Service (拒绝服务) | 攻击者通过大量请求或复杂查询耗尽系统资源。 | API速率限制；会话级的Token预算分配（`src/llm/token_budget.py`）；`max_iterations`硬上限守卫；长任务使用异步和流式处理。 |\n| **E**levation of Privilege (权限提升) | 普通用户执行管理员操作；LLM通过提示注入获取系统级权限。 | 严格的RBAC模型（预留）；工具调用权限隔离（`read/write/execute/network`）；禁止`eval`/`exec`；LLM输出经结构化校验后再进入下一环节。 |\n\n特别地，面对**Prompt Injection**攻击，系统采取了多重防护：\n- **输入验证**：所有用户输入和工具参数先经过Pydantic模型校验。\n- **工具隔离**：MCP工具权限体系要求LLM显式声明所需权限，防止模型通过工具调用执行越权操作。\n- **输出校验**：工具调用的结果在传递给下一个LLM或工具前，需通过结构化校验，防止被污染的模型输出影响系统。\n\n### 10.5. 合规要求：个保法与GDPR\n\n系统设计严格遵守**《中华人民共和国个人信息保护法》（PIPL）** 和**欧盟通用数据保护条例（GDPR）** 的核心原则。\n\n-   **最小化收集**：系统仅收集提供服务所必需的最少用户信息。`src/api/ip_user_resolver.py` 中的`resolve_user_id`函数，在无明确用户ID时，会基于客户端IP生成一个确定性的但不可逆的`user_id`，避免直接存储原始IP。\n-   **目的限制**：除了用户身份，不收集其他无关个人信息。用户上传的文件和会话内容，只会用于生成研究报告，不会用于任何其他目的。\n-   **数据保留与删除**：会话设置TTL（默认30天），过期后自动清理。报告存储支持用户显式删除。所有操作均遵循“数据是用户的”原则，提供完整的删除接口。\n-   **数据隔离**：如前文所述，`agent_id` + `user_id` + `session_id`三级隔离策略确保不同租户之间的数据完全隔离，防止数据混用。\n-   **数据跨境**：系统提供MCP工具协调机制，但通过配置和文档提醒用户注意，当使用如`pinecone`、`openai`等境外SaaS服务的MCP工具时，可能会触发数据出境。系统本身（`src/skills/researcher/mcp_coordinator.py`）当前未对工具入参/出参做PII自动脱敏，这是一个已追踪的安全合规风险点，未来将通过增加PII过滤中间件来解决。\n\n### 10.6. 审计日志与不可篡改\n\n审计日志是安全合规的基石。系统对所有关键操作进行记录，并确保日志的完整性和不可篡改性。\n\n**审计覆盖范围：**\n-   **用户操作**：登录、登出、报告创建/浏览/删除、文件上传、MCP配置变更。\n-   **系统事件**：模型调用（含耗用的Tokens和费用）、工具调用、数据检索、关键异常。\n-   **管理操作**：用户权限变更、系统配置修改。\n\n**不可篡改性实现：**\n审计日志存储在PostgreSQL的专门表中（如`audit_logs`）。其不可篡改性通过以下机制保障：\n1.  **仅追加（Append-Only）**：系统没有提供任何可以修改或删除审计日志记录的API接口。写入操作使用`INSERT`语句，且程序逻辑保证不对已有记录进行`UPDATE`或`DELETE`。\n2.  **幂等初始化**：`src/memory/db_initializer.py` 中的`init_db`函数，使用`CREATE TABLE IF NOT EXISTS`幂等创建审计日志表，避免因并发启动导致表结构异常。\n3.  **连接池与事务**：PostgreSQL的`asyncpg`连接池和事务管理保证了审计日志写入的原子性和一致性，防止因部分失败导致日志丢失。\n4.  **哈希链（规划中）**：为了进一步提升抗篡改能力，未来计划在每条日志记录的哈希值中，包含前一条记录的哈希值，形成链式结构。任何对早期记录的修改都会导致后续所有记录的哈希校验失败。\n\n通过以上设计，系统为安全运维、事后溯源和合规审计提供了坚实、可信的数据基础。\n\n---\n\n## 11. 用户界面设计(如适用)\n\n本章节定义 AgentInsight Researcher 前端的用户界面设计，包括信息架构、关键页面与组件、交互流程、用户旅程以及设计规范与响应式断点策略。当前系统包含独立的生产级前端应用，位于 `frontend/` 目录，基于 Next.js 15 + React 19 + shadcn/ui + Zustand 构建。\n\n### 11.1. 信息架构与导航结构\n\n前端信息架构遵循“会话-对话详情”的层级模型，核心路径为：登录 -> 会话列表 -> 对话界面 -> 流式渲染结果与工具调用展示。辅助功能页面包括设置、MCP配置管理，通过统一的侧边栏或顶部导航访问。\n\n**层次结构**：\n- **一级**：登录/注册（`/login`, `/register`）、主应用（`/`）、设置（`/settings`）、MCP配置（`/mcp/researcher/setting`）。\n- **二级（主应用内）**：会话列表（侧边栏）、当前会话对话流（主内容区）。\n- **三级（对话流内）**：消息列表（用户/助手/工具调用/来源/审核）、流式文本渲染区、节点进度展示。\n\n**导航结构**：\n- **主导航**：左侧侧边栏，包含会话列表（新建/切换/删除/重命名）、用户菜单（登出）。\n- **次导航**：顶部栏，包含 Bot 图标、设置入口、MCP 管理入口。\n- **面包屑**：不适用，应用为单页深度交互模式。\n\n导航状态由 `nav-store` (Zustand) 管理，侧边栏的展开/折叠、当前活动会话 ID 等状态持久化到 localStorage。\n\n用户体系支持 JWT 双重验证（httpOnly cookie + localStorage），通过 `auth-store` 管理登录态。当 `NEXT_PUBLIC_SELF_HOST` 为 true 时，Next.js middleware 跳过登录守卫，直接进入主应用。\n\n多 Agent 路由采用 Nginx 按路径分发方案（方案B），`agents.config.ts` 定义各个 Agent 的路由配置。前端通过 `/api/proxy/[...path]` route handler 代理后端所有 API 请求，WebSocket 路径格式为 `/v1/ws/{agentName}/{sessionId}`。\n\n### 11.2. 关键页面与组件\n\n**1. 登录/注册页面 (`/login`, `/register`)**\n- 支持密码登录、短信验证码、图片验证码。\n- SELF_HOST 模式下自动跳过（middleware 逻辑）。\n- Token 双重存储：httpOnly cookie + localStorage。\n\n**2. 主聊天界面 (`/`)**\n- 核心页面，采用“会话列表 + 对话流”左右布局。\n- **会话管理组件**：侧边栏会话列表，支持新建（默认 `detailed_report` 报告类型）、切换、删除、重命名。会话列表持久化到 localStorage，会话级草稿/文件/流式状态隔离（切换会话时保留各自上下文）。\n- **消息列表组件**：使用 `React.memo` 包裹单条消息，通过 `useShallow` 浅比较 selector 避免全 store 订阅。消息区分 user / assistant，支持 Markdown 渲染（`ReactMarkdown` + 模块级 plugins 常量）。\n- **输入框组件**：透明背景，无 focus 边框（`outline: none`），支持 Enter 发送、Shift+Enter 换行。用户消息宽度优化 `max-w-[95%]`。\n- **流式渲染组件**：基于 Vercel AI SDK `useChat` hook + 原生 SSE 流式渲染，实现逐字/逐块追加。支持实时流式显示、“生成中”状态、RAF batching（避免 O(n²) 重渲染）。\n- **工具调用组件**：折叠面板，通过 SSE 自定义事件 `event: tool_call` 接收并展示工具名、参数、结果摘要。\n- **检索来源组件**：折叠面板，通过 SSE 自定义事件 `event: sources` 展示召回片段（source + score）。\n- **节点进度展示组件**：8 类结构化 WebSocket 消息（logs / content / node_progress / sources / tool_call / report / human_feedback_request / error），用于展示 Agent 协作流水线各阶段进度。\n- **人在回路审核组件**：当 `human_review_enabled=True` 时，显示审核对话框，接收并提交研究计划/大纲反馈（WebSocket `human_feedback_request`）。\n\n**3. 设置页面 (`/settings`)**\n- 报告格式（PDF/DOCX/Markdown）、类型、语言、风格、Tone 配置。\n- 配置数据通过 `/api/proxy/...` 传递到后端。\n\n**4. MCP 配置管理页面 (`/mcp/researcher/setting`)**\n- 多 tab 布局：“MCP 服务” + “智能体配置”。\n- 垂直 tab 布局：“我的服务” + “仓库”（系统预置的 MCP）。\n- MCP 服务列表 CRUD 操作，按 `agent_id` + `user_id` 数据隔离。\n- 系统级 MCP 预置（23 个系统 MCP，`is_system=TRUE`）。\n\n**5. 历史报告面板 (`history-report-panel`)**\n- 模块级缓存 + stale-while-revalidate 策略，避免重复 API 请求。\n- 报告下载与预览（多格式下载链接）。\n\n### 11.3. 交互流程用户旅程\n\n**典型用户旅程：发起研究请求**\n\n1. **登录**：用户访问 `/login`，输入凭据或通过 SELF_HOST 模式自动跳过。\n2. **进入主界面**：`/` 路由展示侧边栏（会话列表）和主内容区。若无可用的会话，自动新建一个，默认报告类型为 `detailed_report`。\n3. **新建会话（可选）**：点击侧边栏“新建会话”按钮，生成新的 UUID 会话 ID，清空对话框。\n4. **输入研究请求**：在输入框中输入自然语言查询，按 Enter 或点击发送按钮。\n5. **发送与流式渲染**：\n   - 前端通过 `POST /api/proxy/v1/chat/completions` 发送请求（`Authorization: Bearer <JWT>` 或 IP-based user_id 降级）。\n   - 后端识别为 RESEARCH 意图，触发研究流水线。\n   - 前端实时接收 SSE 流式数据，逐块渲染到消息列表。\n   - 同时展示节点进度（8 类 WebSocket 消息）、工具调用（折叠面板）、检索来源（折叠面板）。\n6. **人在回路（条件分支）**：若 `human_review_enabled=True`，Agent 进入审核节点，WebSocket 推送 `human_feedback_request`，前端显示审核对话框。用户选择“接受”或输入修订意见，提交后继续流水线。\n7. **报告生成**：LLM 生成最终报告，sources 和 report_id 随流式数据返回。报告下载链接出现在消息底部。\n8. **会话管理**：用户可切换会话（保留各自上下文）、重命名、删除。切换时通过 `AbortController` 取消未完成请求（竞态保护）。\n9. **查看历史**：可查看当前用户历史报告列表（基于 `user_id` + `agent_id` 数据隔离）。\n\n**并发与错误处理**：\n- 并发研究请求：`MAX_BACKGROUND_STREAMS=1`，超过时采用 LRU 驱逐策略 + 用户确认弹窗。\n- 错误处理：网络错误/超时/HTTP 非 2xx 在页面前端显式提示（错误状态消息）。\n\n### 11.4. 设计规范与响应式断点\n\n**设计系统**：Linear Indigo 设计系统\n- CSS 变量定义主题：`light` / `dark` 双主题切换。\n- Tailwind CSS 类名 + 自定义 CSS 变量，覆盖全局配色。\n- 主对话区背景：`--bg-card`（白色），消除割裂感。\n- 侧边栏：`--bg-sidebar`（浅灰色），与主对话区形成层次感。\n- 输入框：透明背景，focus 状态无边框。\n- 自定义 Tooltip 组件（10+ 文件统一）：基于视口边界动态定位，替代原生 `title` 属性。\n- 组件库：shadcn/ui（包含 button、dialog、popover、select 等基础组件）。\n\n**响应式断点策略**：\n\n| 断点 | 设备 | 布局变化 |\n|------|------|----------|\n| `< 768px` | 移动端 | 侧边栏隐藏，通过汉堡菜单或底部导航切换；输入框宽度自适应；消息气泡宽度 100% |\n| `768px - 1024px` | 平板 | 侧边栏可折叠（默认收起），主内容区全宽；消息列表 `max-w-[95%]` 优化 |\n| `>= 1024px` | 桌面端 | 全功能侧边栏展开 + 主内容区；工具调用与来源面板可并排展示 |\n\n- 侧边栏：移动端通过覆盖层（overlay）临时拉起，避免占用显示空间。\n- 输入框：所有断点保持透明背景，`max-w-[95%]` 从右向左填充。\n- Tooltip：基于视口边界动态定位，防止移端端溢出。\n\n**性能与交互细节**：\n- **RAF batching**：流式渲染采用 `requestAnimationFrame` 批量处理，避免 O(n²) 重渲染。\n- **`useShallow`**：Zustand 状态管理中使用浅比较 selector，避免全 store 订阅导致的不必要渲染。\n- **`React.memo`**：单条消息组件使用 `React.memo` 包裹，props 不变时跳过重渲染。\n- **`skipHydration: true`**：部分组件在 SSR 时跳过 hydration，避免客户端/服务端渲染不一致。\n- **稳定性优化**：模块级空数组常量（解决 `useSyncExternalStore` 无限循环 #185）、模块级 plugins 数组（避免 `ReactMarkdown` 重解析）、`AbortController` 竞态保护。\n\n---\n\n## 12. 测试策略\n\n### 依赖注入实现\n\n- **LLM 网关**：`src/llm/client.py` 中的 `LLMClient` 类接收一个 `config` 参数（`LLMConfig` 类型），而非硬编码模型列表或 API Key。在单元测试中可注入一个 `FakeLLMClient`，返回预定义的文本或异常。\n- **数据库连接池**：`src/memory/checkpointer.py` 中 `PostgresSaver` 的构造器接受已初始化的异步连接池（`asyncpg.Pool`），而非内部创建。测试时可通过 `create_test_pool` fixture 连接本地临时 Postgres 或使用 `aiosqlite` 模拟。\n- **Qdrant 客户端**：`src/rag/qdrant_manager.py` 的 `QdrantManager` 接受 `QdrantClient` 实例和配置参数。测试中可注入 `FakeQdrantClient`（基于内存字典实现 subset 功能）或指向独立测试集合。\n- **搜索引擎与抓取器**：`src/skills/searchers/` 和 `src/skills/scrapers/` 各自遵循工厂模式，通过 `BaseSearcher` / `BaseScraper` 抽象类定义接口。`src/skills/research_conductor.py` 通过构造函数接收 `searcher_factory` 与 `scraper_factory`，可替换为返回 mock 对象的工厂。\n\n#### 12.2.2. Mock 策略\n\n依据测试层级定义明确的 mock 范围：\n\n- **单元测试**：mock 所有网络 I/O。使用 `pytest-mock` 的 `mocker.patch` 替换 `httpx.AsyncClient.post`、`aioredis.Redis.get` 等。对于 LiteLLM 调用，直接 mock `src.llm.client.LLMClient.achat` 返回 `AsyncIterator`。示例：\n\n```python\n# tests/unit/test_query_classifier.py\nasync def test_classify_research(mocker):\n    mock_llm = mocker.patch("src.llm.client.LLMClient.achat")\n    mock_llm.return_value = async_iter(["RESEARCH"])  # 自定义辅助函数\n    classifier = QueryClassifier(llm_client=mock_llm)\n    result = await classifier.classify("分析今年AI行业趋势")\n    assert result == Intent.RESEARCH\n```\n\n- **功能/API/e2e 测试**：避免 mock 外部服务，依赖真实容器。仅在以下场景使用有限 mock：\n  - 模拟 LLM 响应以加速收敛（但需保留至少一个用例调用真实 LLM 验证格式）。\n  - 外部服务不可用时（如搜索引擎 API 配额耗尽）回退 mock。\n  - 时间相关逻辑（如 TTL 过期）使用 `freezegun` 或 `pytest-timeout`。\n\n- **集成点测试**：`tests/unit/` 下允许少量集成测试（如测试 `QdrantManager.upsert` 与 `search` 的映射逻辑），但必须 mock 通信层（`QdrantClient.grpc_points`），不依赖 Qdrant 实例。\n\n### 12.3. 测试数据管理\n\n测试数据遵循 **隔离、可重复、自动清理** 三大原则。所有持久化层均按测试场景使用唯一前缀命名空间，避免测试用例间相互污染。\n\n#### 12.3.1. 数据生成策略\n\n- **Faker 库**：使用 `faker` 生成用户友好的模拟数据，包括用户 ID、会话标题、报告内容摘要等。所有测试模块共享一个 `Faker` 实例（`tests/conftest.py` 中配置 locale `zh_CN`），确保生成字段符合业务格式（如手机号、邮箱、公司名）。\n- **工厂模式**：基于 `pytest-fixture` 的工厂函数创建测试对象。例如 `tests/factories/session_factory.py` 提供 `create_test_session(session_id)`，内部调用 `session_store.create_session()` 写入 Postgres。对于 Qdrant 数据，提供 `create_test_qdrant_point(agent_id, user_id)` 工厂，自动设置 `namespace=test_{agent_id}_{user_id}`。\n\n```python\n# tests/factories/report_factory.py\nasync def create_test_report(\n str(uuid.uuid4())\n    await report_store.save_report(\n        report_id=report_id,\n        agent_id=agent_id,\n        user_id=user_id,\n        session_id=session_id,\n        content=content\n 集合**：每个测试用例使用 `namespace=test_{agent_id}_{user_id}`。`src/rag/qdrant_manager.py` 的 `search` 方法强制 namespace 参数，测试 fixture 在 teardown 中调用 `qdrant_manager.delete_namespace()` 清理。\n- **Postgres 业务表**：测试用例插入的数据行通过 `agent_id` 和 `user_id` 限定为 `test_*` 模式。测试结束时，通过 `DELETE FROM research_reports WHERE agent_id LIKE 'test_%'` 进行清理（在 `conftest.py` 中的 `pytest_sessionfinish` 钩子中执行）。\n- **Redis 缓存**：使用 `cache_prefix` 配置 `test_cache:`，避免与生产缓存冲突。可在 `conftest.py` 中通过 `redis_client.flushdb()` 清理所有测试相关键（需确认 Redis 实例为专用测试实例或使用 DB 1）。\n\n#### 12.3.3. 测试数据生命周期\n\n每个测试函数级 fixture 负责数据创建与销毁：\n\n```python\n# qdrant_manager.create_collection(namespace)\n    await qdrant_manager.upsert_points(namespace, [test_point])\n    yield namespace\n    # 清理\n    await CI 集成测试\n\n测试流水线深度集成于 CI/CD 流程，采用 GitHub Actions 作为主要 CI 平台，遵循严格的阶段顺序与失败阻断策略。\n\n#### 12.4.1. 流水线阶段\n\n1. **代码检查与构建**：每次 push 触发。运行 `pylint`、`mypy` 静态检查，然后执行 `docker build -t agent:test` 构建镜像。此阶段同时运行单元测试：\n   ```bash\n   cd src && pytest tests/unit/ -q --cov=src --cov-report=xml --asyncio-mode=auto\n   ```\n   单元测试失败即终止流水线，不继续后续阶段。\n\n2. **容器栈启动**：使用 `docker compose -f docker-compose.ci.yml up -d` 启动全部 7 个容器（agent、embeddings、qdrant、redis、postgres、searxng、可选 rerank）。等待所有服务健康检查通过（最大超时 120 秒），超时则标记失败。\n\n3. **功能测试**：向容器栈的 agent 服务发送测试请求，执行 `pytest tests/functional/ -q --junit-xml=report-functional.xml`。失败则阻断后续阶段。\n\n4. **API 测试**：`pytest tests/api/ -q --junit-xml=report-api.xml`。包含正向（正确 Token 与参数）与逆向（无 Token、参数越界、限额超限）场景。\n\n5. **回归测试**：`pytest tests/regression/ -q --junit-xml=report-regression.xml`。此阶段为合并门禁，不允许跳过。\n\n6. **端到端测试**：`pytest tests/e2e/ -q --junit-xml=report-e2e.xml`。仅在所有前置阶段通过后执行，避免容器资源浪费。\n\n7. **结果汇总**：所有测试报告（JUnit XML）上传至 GitHub Actions Artifacts，同时生成覆盖率报告（Codecov）。若任一阶段失败，PR 标记为 "do not merge"。\n\n#### 12.4.2. 环境变量注入\n\n- `AGENT_URL`：测试目标地址，默认 `http://agent:8066`，通过 CI 变量覆盖。\n- `TEST_LLM_MODEL`：指定测试用 LLM 模型（如 CI 运行使用独立的 `run_id` 构建测试数据前缀，避免跨 PR 污染。\n- 集成测试阶段采用 `pytest-xdist` 的 `-n auto` 提升并行速度，但需确保数据库与 Qdrant 的 connection pool 大小足够。\n- 所有测试结束后，`docker compose down -v` 清除容器与卷，避免磁盘膨胀。\n\n#### 12.4.4. 门禁规则\n\n- 合并 main 前必须通过回归测试与端到端测试。\n- 每月一次全量 E2E 回归（包含所有搜索引擎与抓取器）在凌晨执行，结果发送团队告警。\n- 单元测试覆盖率阈值：核心模块（`src/skills/`、`src/rag/`、`src/llm/`）不低于 85%，整体不低于 70%。CI 阶段通过 `pytest-cov` 检查，不达标则失败。\n\n---\n\n##
